# 2026-10-30（07）第一次接上真模型：从 0% 到 75%，以及一个不报错的错

> 用户在 `.env` 里配好 DeepSeek Key 后跑 `llm_smoke.py`，12 句全挂（0.0%）。
> 三次迭代之后同一批句子：**真模型 75.0%，mock 75.0%**。
> 但过程中挖出两件比「听懂率」重要得多的事：
>
> 1. 第一轮全挂时，错误信息是 `HTTPStatusError` —— 既看不出是 Key 的问题还是限流。
> 2. 修好之后出现了一类**不报错、不抛异常、语气正常、结论是错的**回答。
>    原文是「近 30 天没有支出记录」，而账上明明有 11 笔支出。
>
> 本文事实与推断分节，复现命令附在文末。

---

## 一、事实

### 事实 1：第一轮 12 句全挂，且错误信息指不出原因

用户实跑输出的每一行都是：

```
real · 其他(说明类)   理解模块暂时不可用（HTTPStatusError），请稍后再试。
汇总：真模型一次听懂率 0.0%   平均耗时 2473 ms/句
```

`HTTPStatusError` 是 `httpx` 的异常类名。它把 401（Key 错）、400（参数错）、
429（限流）、5xx（服务端）压成了同一个字符串。演示当天真遇到这行，
只能猜。

### 事实 2：「偶发」是重试能救回来的

单独用 `httpx` 打最小 payload 能复现 400，但把真实 SYSTEM_PROMPT +
`response_format` 原样打过去是 200。也就是说那一轮批量失败不是配置错，
更像短时间内的限流/服务端抖动。

改法（`app/llm/openai_compat.py`）：

- `_post()` 对 429 / 500 / 502 / 503 / 504 退避重试（1.5s、3s），4xx 里其余状态码直接抛；
- `LLMError` 携带 **HTTP 状态码 + 端点原话**（`error.message`）；
- 抛出来的话直接进用户可见的回复：「理解模块暂时不可用：HTTP 401：Invalid API key」。

改完再跑：**66.7%**（8/12）。

### 事实 3：★ 安静地答错 —— 比崩溃危险的那一类

66.7% 这一轮的输出里有一行：

```
我上个月点外卖花了多少钱
   mock ✅ 办到(analyze_spending)   近 30 天共 12 笔交易，支出合计 ¥10,912.00。
   real ✅ 办到(analyze_spending)   近 30 天没有支出记录。      ← ★
```

`recent_transactions` 明明返回了 12 笔（11 笔支出）。把模型生成的代码原样跑一遍：

```
result: {'window_days': 30, 'total_out_cents': 1091200, 'category_count': 5,
         'breakdown': [{'category': '其他', ...}]}
```

**算得对，键名不对。** 表述层读 `result["rows"]`，拿到空列表就打印
「没有支出记录」。没有异常、没有日志、没有告警——用户看到的是一句
语气完全正常的错话。

比这更早的一次是同一类：生成的代码用了 `datetime.strptime`，
沙箱不允许 import，于是 `NameError` → 这次至少崩了，还看得见。

### 事实 4：NLU 缺口（提示词没写全，不是模型不行）

| 用户原话 | 修前 | 根因 |
|---|---|---|
| 把爱奇艺退了吧 | `P-010（merchant: Field required）` | 提示词只列了**工具名**，没给参数表 |
| 帮我看看有没有乱扣费 | 反问「要看多长时间」 | 没写「没给时间范围就默认 30 天」 |
| 余额够的话给王强转 500 | 只做了第一步查余额 | 提示词从未描述过条件步骤 `when` |

改法：工具参数表从 `REGISTRY` **现场生成**（与工具定义同源，加参数不会漏改提示词）、
`ARG_HINTS` 逐字段给约定、`when` 写进示例并注明「只允许四个字段、不许写表达式」。

### 事实 5：契约校验 + 模板回落（`codegen.validate_result` + `tools/analysis.py`）

规则：模型可以自由写代码，但 `result` 必须对得上表述层的契约。
对不上 → 用确定性模板重算，并把这次回落如实写进 `sandbox.fallback` 与回复末尾。

```
（注：模型生成的代码缺少 rows 列表（字段名必须是 rows），已改用确定性模板重算，数字以本结果为准。）
```

**不静默替换**是刻意的：数字对了，但「是谁算的」变了，这件事用户有权知道，
审计链也必须能复现。

### 事实 6：★ 结构对了，判据也可能坏

契约校验上线后，`anomalies` 仍然给出了这个：

```
近 30 天扫描 11 笔支出，发现 11 笔异常，涉及 ¥10,912.00
```

把模型写的代码读出来，找到了原因：

```python
def is_foreign(cp):
    for ch in cp:
        if ch not in "abcdefghij...有限公司科技商贸文化传媒服务咨询中心店":
            return True          # ← 汉字「美」「团」「瑞」不在白名单里 → 判成陌生商户
```

于是瑞幸咖啡、美团外卖、京东全被标成「陌生商户」。结构合法、字段齐全、
数字自洽——校验器看结构是看不出来的。

两条补丁：

1. **把判定条件逐字写进契约**（「深夜」= 0:00–5:59；「大额」= ≥100000 分；
   「陌生商户」= 商户名为空或含「未知」；「境外商户」= 含「境外」），
   并明写一句「商户名里出现汉字、英文品牌名都不算陌生商户」。
2. **不靠模型自述，改由校验器交叉核对硬线索**：深夜 / 大额 / 含「未知」/ 含「境外」
   这四类交易只要有一笔没出现在结果里，就判为「判据与目标定义不符」→ 回落；
   外加一条「全中 = 判定条件等于没生效」。

改完复测同一句：`scanned 11, count 3, ¥9,990.00`，与模板一致。

### 事实 7：终局数字（2026-10-30 实跑）

```
真模型一次听懂率  75.0%   追问 3 / 听不懂或异常 0 / 共 12
mock  一次听懂率  75.0%   追问 3 / 听不懂或异常 0 / 共 12
平均耗时 2303 ms/句   峰值 4535 ms/句
无超时 / 无非法 JSON / 无未注册工具
```

口径按 `05_评审视角自检.md`：追问与听不懂都不计入分子。
未计入的 3 句是真模型**主动追问**，不是听不懂：

| 句子 | 真模型 | 归类 |
|---|---|---|
| 再给他转100 | 追问缺收款人（且指出「他」指代不明） | 追问 |
| 明天把房租转给房东 | 追问缺金额 | 追问 |
| 帮我把钱都归拢一下 | 「不确定具体指什么，是想汇总余额、集中资金还是赎回理财？」 | 追问 |

★ 这里修掉了一个**指标本身的口径 bug**：`llm_smoke.py` 原来靠「回复里有没有
『还差…请补充』」判断是不是追问。这两句是 mock 生成的固定文案，真模型生成的
追问不含这两个字，于是同样的行为被记成「其他（说明类）」、算进未听懂。
现在 `TurnResult` 多了一个 `clarify` 字段，**由引擎直接说是追问**，
不再让统计脚本去猜文案。

### 事实 8：验收仍然绿

```
selfcheck.py ：demo 50/50 · pytest 125 passed · eval 31/31 vs 19/31 · 沙箱 11/11
```

新增 `tests/test_codegen_contract.py` 13 条，钉住：模板自己满足契约、
缺 `rows` 被拒、有支出却返回空被拒、漏扫被拒、全中被拒、漏标深夜/大额被拒、
回落路径写出 `sandbox.fallback`、合格产物不被滥杀。
另加 2 条（`tests/test_nlu.py`）钉住 `TurnResult.clarify`：追问的那一轮必须标出来，
办完的那一轮不许被误标。

## 二、推断（以下不是实测，标明是判断）

1. **75% vs 75% 不等于「真模型与 mock 等价」。** 12 句样本，差 1 句就是 8.3 个点；
   两者的失败方式也不同——mock 的失败来自词表，真模型的失败来自猜不准指代。
   要下「真模型更好/更差」的结论，样本至少要到几十句，并固定同一批句子。
2. **模型代码可用率（4 个 goal 单轮全部通过契约）只是一个采样点。**
   同一句问第二遍可能又是另一种写法。契约校验的价值恰恰在于：**不依赖它每次都写对**。
3. **演示时要能说清「这一轮的分析代码是谁写的」。** 一旦发生回落，数字来自模板。
   这不影响结论正确性（模板是同一口径的确定性实现），但讲述时必须如实：
   「模型写了代码、沙箱跑了、契约不符时用模板兜底并标注」——这也正好是
   「LLM 只提案、内核做裁决」的又一个例证，比藏着更有说服力。
4. **判据交叉核对只能覆盖「定义里写死的」那几条。** 「陌生商户」这种需要业务口径的，
   靠的是把口径写进契约；真实银行场景里这类口径有几十条，规模一上来就需要
   一个领域词典/规则库，而不是继续往提示词里堆。
