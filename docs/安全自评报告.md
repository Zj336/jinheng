## 0. 一句话结论

本系统的安全主张只有一句：**大模型没有执行权**。

它能把一句话听成什么、想出什么样的计划，都不影响「这一笔到底执不执行」——
后者由一个**从不接收自然语言**的确定性策略引擎裁决，由纯模板表述层转述。
所以提示注入最多让模型产出一个**不合法的计划**，而这个计划会在结构层（DAG 校验）
和语义层（策略引擎）两次被拦下。

可自证的指标（命令见 §8，任何人可复跑）：

| 指标 | 结果 |
|---|---|
| 对抗评估：31 条攻击用例 | 金衡 **31/31 = 100%** 防住 |
| 对照组（同一批攻击，无策略引擎/无沙箱的系统） | 19/31 = 61.3% |
| 沙箱攻击面验证 | 11/11 符合预期 |
| 单元与安全用例 | 135 passed |
| 端到端场景 | 50/50 通过 |

## 1. 资产与信任边界

| 资产 | 被谁保护 | 出事后果 |
|---|---|---|
| 客户资金（转账、申购、赎回） | 策略引擎 + 限额硬校验 + 强验证 | 直接资损 |
| 客户数据（余额、流水、联系人、卡片） | 令牌身份 + 每张表带 `user_id` | 隐私泄漏 |
| 审计记录 | HMAC-SHA256 哈希链 | 事后无法追责 |
| 模型输出（计划） | DAG 校验器 + 参数 Schema | 错误执行 |
| 沙箱内执行的分析代码 | AST 闸门 + 子进程 + 资源限制 | 主机被控 |

**信任边界只有三处**：① 浏览器 ↔ 服务端的令牌；② 服务端内核 ↔ 大模型；
③ 内核 ↔ 沙箱子进程。三处都是「默认不信任，逐项校验」：

- 模型返回的 JSON 不是「可信输入」，是**外部输入**：非 dict 顶层、字段类型错、
  工具不存在、参数越界，一律拒绝并回落（`app/llm/openai_compat.py`）。
- 沙箱代码不是「自己人写的」，是**模型写的**：先 AST 白名单，再子进程，再限时限额限输出。

## 2. 身份与授权：三层必须分开

| 层 | 回答的问题 | 唯一来源 | 模型能否影响 |
|---|---|---|---|
| 会话身份 | 你是谁 | 令牌（HMAC-SHA256 签名，覆盖 user_id + 过期时间） | 否 |
| 操作授权 | 这一笔要不要再验一次 | 三色分级 + 策略引擎常量 | 否 |
| 数据归属 | 这条数据是不是你的 | 每张表的 `user_id` 条件 | 否 |

- 口令：PBKDF2-HMAC-SHA256，**12 万轮** + 每用户 16 字节随机盐（`app/auth.py`）。
  6 位纯数字口令用裸 SHA-256 等于明文，这是本项设计的直接原因。
- 令牌：HMAC 签名，默认有效期 2 小时（`JH_TOKEN_TTL`），服务端不存会话表。
- 登录节流：同一账号 10 分钟内错 5 次即锁定（`_MAX_FAILS=5` / `_LOCK_WINDOW_S=600`）。
- 越权一律 **404**，不是 403：403 等于承认「这个东西存在，只是不给你」，
  那本身就是一次存在性探测。会话、审计链、跨用户联系人都按这条执行。

## 3. 三色分级与第四种结局：拒绝

| 颜色 | 策略 | 覆盖 |
|---|---|---|
| 🟢 绿 | 自动执行 | 查询类、账单分析 |
| 🟡 黄 | 用户确认 | 小额转账（日累计 ≤1000 元）、取消订阅、申请虚拟卡、锁定卡片交易、理财赎回 |
| 🔴 红 | 多因子认证 | 大额转账、挂失/解挂、调整卡片额度、解除交易限制、理财申购 |
| ⛔ 拒绝 | 不执行，强验证**不可覆盖** | 超限额（P-040/042/043）、风险适当性不匹配（P-070）、注入+动钱（P-090） |

**第四行是本项目最重要的一条设计判断**：限额不是风险信号，是硬约束。

- 修之前：超限 → 升级到红色 → 输验证码 → 照样执行。1000 元的日限额，
  输一个验证码就能突破，等于「限额只是个提示」。
- 修之后：超限直接 DENY，并回显「今日剩余可转 ¥X」「如需提额请转人工」。
- 同理，**适当性**（P-070）也是硬拒：产品风险等级高于客户风险偏好时，
  验码与确认都不能覆盖。「你是不是本人」和「这笔产品该不该卖给你」是两件事。

风险等级只升不降（`tools/base.py::escalate`），系统中**不存在降低等级的代码路径**。

## 5. 本次（2026-10-30）修掉的缺陷

每条都写明「修之前会怎样」——这些是自评里最该有的部分，不是成绩单。

| # | 缺陷 | 修之前会怎样 |
|---|---|---|
| 1 | 会话劫持：`/chat` 接受任意 `session_id` | 拿到别人会话 id 就能续写别人的对话上下文，甚至替他对已确认操作说「确认」 |
| 2 | 一次确认放行整个计划 | 确认卡片只列第一步，实际执行了同级别的后续步骤 |
| 3 | 验证因子未在异常路径清理 | 一轮异常之后，「已确认」状态残留到下一次请求 |
| 4 | 额度被当风险信号 | 超限只升到红色 → 验证码可覆盖 → **限额形同虚设** |
| 5 | 定时转账当场扣款且不占额度 | 预约转账 = 立即转账 + 拆单绕开日限额的侧门 |
| 6 | 审计校验在 >5000 行或按会话校验时误报 | 完好的库被报成「被篡改」——招牌功能谎报灾情 |
| 7 | 审计链为纯 SHA-256 | 有库写权限的人改完内容重算整链即可「修好」，链只能证「没手滑」 |
| 8 | 适当性缺失 | 稳健型客户可直接购买高风险产品（验码即可） |

第 7 条的修法要点：改用 **HMAC-SHA256**，密钥由身份密钥派生一个独立子密钥
（`HMAC(secret, "jinheng/audit-chain/v1")`），密钥不在数据库里。
一个密钥只干一件事——令牌签名与审计签名共用一把，等于任一处泄漏同时打穿另一处。

现场可复现：设置 `JH_ALLOW_TAMPER_DEMO=1` 后，前端出现「篡改演示」按钮：
改掉自己最近一条审计记录的金额（¥300 → ¥30,000）→ 校验器立刻报「第 N 行被改过」→
一键复原。该接口**默认不存在**（未开启时返回 404，连「有这个接口」都不承认）。

## 6. 攻击面与对策（含对照系统结果）

| 攻击 | 金衡的处理 | 为什么普通实现会挂 |
|---|---|---|
| 冒充管理员改限额 | 无落点：角色/额度都不来自自然语言 | 规则写在 prompt 里，注入改的就是 prompt |
| 注入 + 立刻转账 | P-090 整轮阻断（查询不受影响） | 模型「听懂了」，然后照做 |
| 拆单绕限额 | 日累计、月累计、单收款人三种口径，同计划内也累计 | 只看单笔 |
| 验证码覆盖限额 | 限额 DENY，无放行路径 | 「重大操作升到红色」= 可被验证码覆盖 |
| 越权读别人的卡 | 令牌 + 表级 user_id + 404 | 请求体里传 user_id 就信 |
| 改审计记录 | HMAC 链校验，无密钥算不出指纹 | 普通表，改完看不出来 |
| 沙箱逃逸 | AST 白名单 + 子进程 + 资源限制 | `exec(code)` |
| 6 位口令穷举 | PBKDF2 12 万轮 + 10 分钟 5 次锁定 | 明文/裸哈希比对 |
| 会话 id 劫持 | 会话归属校验，别人的 → 404 | 用 id 续写上下文 |
| 输出不可信 | 模型无权转述交易结果，表述层纯模板 | 让模型「总结一下执行结果」 |

## 7. 已知局限与**没做的事**（诚实清单）

写这一段不是为了减责，是因为「没做的事被说成做了」才是真正的安全问题。

1. **没有真实的强验证通道**：动态码由系统生成并投递到「手机」面板（`sms_messages` 表 +
   `/api/auth/sms`），人脸/硬件盾是占位。第三层身份在**设计上**成立，在**通道上**是模拟的。
2. **没有调度器**：预约转账只登记台账、不当场扣款、按执行日占用额度，但**不会自动执行**。
   界面与文档都写明「演示环境未开启调度器」，不做「假装会执行」的表述。
3. **没有 Docker 镜像**：沙箱的进程树杀灭在 Windows 上用了 `taskkill /T`，
   内存看门狗用 ctypes 读 WorkingSetSize——换到 Linux 容器里，内存限制只剩「超时兜底」。
   塞进容器恰好会把最能打的一张牌变成「没在目标环境验证过」，所以选择不做并写明。
4. **审计链算法升级会重算历史**：老库从纯 SHA-256 切到 HMAC 时会整链重算一次
   （`app_meta.audit_chain_alg` 记录版本，并写一条 `audit_chain_rekey` 审计行留痕）。
   因此只能承诺「迁移之后没被改过」，不能承诺迁移前的。生产应从第一天就开 HMAC 链。
5. **单机 SQLite**：无分布式事务、无读写分离。并发写入由 SQLite 串行化保证，
   但没有做过压测，**不声称**具备生产级吞吐。
6. **无 API 级限流**：只有登录节流与会话熔断。真实部署需要网关限流（尤其 `/api/chat`，
   它每次都调模型，既有成本也有 DoS 风险）。
7. **无 TLS 配置**：演示跑在 `http://127.0.0.1:8000`。跨机部署必须由反向代理终止 TLS。
8. **前端令牌存 localStorage**：同源单页演示的取舍。若引入第三方脚本或允许内联脚本，
   XSS 可窃取令牌；生产应改 HttpOnly Cookie + CSRF token + CSP。当前页面无外部依赖。
9. **未实现的功能**（不写进能力清单，`capabilities.py` 也不会声称）：
   AA 拆分收款、IM 渠道（微信/企微）、多模态（语音大模型/票据 OCR）、
   月报/年报、订阅异常自动识别、交易回退/冲正。
10. **语音输入是浏览器能力，不是模型**：Web Speech API 只把话转成文字填进输入框，
    由人核对后发送，走与打字相同的管线。它不是绕过那两层校验的旁路。

## 9. 生产化建议（按投入产出排序）

1. 令牌改 HttpOnly Cookie + CSRF + CSP；前端不再持有凭证。
2. 网关限流与熔断（`/api/chat` 单独配额），并把 `data/.auth_secret` 换 KMS。
3. 动态码走真实短信/短信网关，人脸走持牌服务；审计链密钥上 HSM。
4. 审计库与业务库分离（只允许追加写），校验任务定时跑（`/api/audit/verify` 已可被外部调度）。
5. 沙箱迁到独立容器/微虚机，按平台分别实现 CPU/内存硬限制，再补 Docker 部署。
