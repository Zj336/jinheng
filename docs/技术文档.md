---

## 1. 设计主张

**大模型只提案，内核做裁决。**

一句话请求的处理被切成两段，中间隔着一道**类型边界**：

```
自然语言 ──► [LLM 层] ──► 结构化 Plan（Step[]） ──► [内核] ──► 执行 / 拒绝
             只能"提案"          Schema 强约束            只认结构，不认语言
```

内核（DAG 校验器 + 策略引擎 + 工具执行器 + 表述层）**不接收任何自然语言**：
「我是管理员」「风控已批准」这类字符串在类型层面就到不了它。
因此提示注入的最好成绩是「产出一个被拒绝的计划」，而不是「绕过一次校验」。

**为什么把「裁决」和「表述」拆开**：如果让模型来「总结一下执行结果」，
那么模型就在**转述**一笔它没执行、也无权执行的操作——「转了 300」这句话会变成
可被注入改写的东西。本项目里所有结论句都由 `render.py` 用模板拼，金额来自数据库整数。

## 3. 核心算法

### 3.1 计划 → 结构校验（`app/engine/dag.py`）

模型返回的 Plan 必须依次通过：

| 检查 | 不通过的后果 |
|---|---|
| `step.id` 形状（`^[a-z][a-z0-9_]{0,31}$`）与唯一 | 拒绝 |
| 步骤数 ≤ 12 | 拒绝 |
| 工具必须在注册表（16 个） | 拒绝（P-001） |
| `depends_on` 必须指向已存在的前序步骤 | 拒绝 |
| 无环（拓扑排序能排完） | 拒绝 |
| 条件 `when` 只允许 `data` 下的标识符路径（如 `count`、`sandbox.elapsed_ms`） | 拒绝 |

条件是**取字段**，不是表达式语言：不允许下标、不允许函数调用。
这条限制是刻意的——任何「可执行的小语言」都是一个新攻击面。

### 3.2 风险裁决（`app/engine/policy.py`）

`adjudicate_plan` 按拓扑序逐个裁决，并在计划内维护 `running_daily`，
所以同一计划里的两笔「各 600」会累计成 1200 而被限额拦下。

单步裁决顺序（**顺序本身就是安全设计**）：

```
锁定期? → 工具白名单 → 参数 Schema → 前置解析（找不找得到 / 适当性）
   → 越权 → 限额硬校验（日 / 月 / 单收款人） → 单笔阈值与首收款人升级
   → KYC → 三色映射 → 一次性放行凭证（只放行被确认的那一步，用过即失效）
```

前置解析排在强验证**之前**，是为了不浪费用户的每一次人脸/短信：
先确认「这操作根本做不成」，再让用户做认证。

限额三条口径都是**从数据库实时聚合**（`transfer_ledger`），不复用内存旧值：

| 规则 | 口径 | 默认阈值 |
|---|---|---|
| P-040 | 当日累计 | 1000 元 |
| P-042 | 当月累计 | 20000 元 |
| P-043 | 单一收款人当日累计 | 1000 元 |
| P-044 | 单笔达到即升红 | 500 元 |

超限 = **DENY**，不是「升级到红色」。分数配色不改变这一点。

### 3.3 分析代码沙箱（`app/sandbox/`）

用户说「分析一下我最近 30 天的消费结构」时，系统真的**生成代码并在沙箱里跑**：

1. **AST 白名单**（`astguard.py`）：节点白名单 + 禁 import + 禁 `eval/exec/open`、
   禁双下划线属性、禁 `datetime`（沙箱内按字符串切片解析时间）。
2. **子进程隔离**（`runner.py`）：独立 `python -I` 子进程，只带受限 builtins。
3. **资源限制**：超时 5 秒；内存 256MB（50ms 轮询 RSS 看门狗：Windows 走 ctypes
   读 WorkingSetSize，Linux 读 `/proc/<pid>/status` 的 VmRSS；两者都由 CI 在
   ubuntu-latest 上实跑验证）；输出上限 64KB；环境变量清空。
   POSIX 下子进程以 `start_new_session=True` 自成进程组，超时/超内存时 `killpg`
   把 fork 出的孙进程一起收走。
4. **产出契约校验**（`codegen.py`）：模型生成的代码产出必须符合固定结构
   （`rows` 每行含 `cents`，类目占比含 `pct_bp`……）。结构不符 → **静默回落**到
   确定性模板，并在回复末尾与 `sandbox.fallback` 里如实标注「这一轮的数字是模板算的」。

> 为什么需要第 4 条：真模型实跑时出现过两次「安静地答错」——JSON 结构对、数字错。
> 契约校验 + 模板回落是这两种错误唯一可靠的兜底。

### 3.4 审计哈希链（`app/bank/db.py`）

```
row_hash[n] = HMAC_K( row_hash[n-1] ‖ \x1f ‖ trace_id ‖ ts ‖ user_id ‖ session_id ‖ stage ‖ payload )
```

- 密钥 `K = HMAC(AUTH_SECRET, "jinheng/audit-chain/v1")`：**独立子密钥**，不进数据库。
  纯 SHA-256 链的死穴是「算法与输入都公开」：有库写权限的人改完内容重算整链即可通过校验。
- 写入用 `INSERT … SELECT` 在写入那一刻取表尾，避免读快照造成的平行链。
- 校验（`verify_audit_chain`）支持三种范围：全库、最近 N 行、单会话。
  窗口从中间截断时起点取窗口首行自己的 `prev_hash`；按会话校验时逐行回查全局前一行。
- 算法版本记在 `app_meta.audit_chain_alg`，升级时整链重算并写一条 `audit_chain_rekey` 留痕。

### 3.5 身份与一次性授权

- 令牌 = `base64(uid.exp).hmac`，TTL 2 小时（`app/auth.py`）。
- `UserContext.verified_for_step`：一次确认只放行**被确认的那一步**，用过即失效。
  这个字段是「一次确认 = 一步」在数据结构上的表达，比任何注释都可靠。

## 4. 数据模型（要点）

| 表 | 关键约束 |
|---|---|
| `users` | `pin_salt/pin_hash`（PBKDF2-12 万轮）；`role`、`risk_pref` 只能由后台/测评写入 |
| `transfer_ledger` | 资金动作台账，`status ∈ {executed, scheduled}`；限额只统计这两个状态 |
| `audit_log` | `prev_hash → row_hash` 链；只追加 |
| `sms_messages` | 动态码通道（与聊天通道分离） |
| `confirmations` | 待确认操作，码与**那一笔**绑定（行里通常整计划） |
| `app_meta` | 审计链算法版本、篡改演示的原文备份 |

金额一律**以「分」为单位的整数**，全系统零浮点；格式化只发生在 `render.yuan()`。

## 5. 交互设计（为什么这样对用户更好）

- **确认卡片摊开**：收款人姓名/银行/尾号、手续费、到账时间、余额转前转后、
  今日剩余额度、是否首转，以及「这次确认只放行上面那一步」。
- **拒绝时说清楚**：超限回显「今日剩余可转 ¥X」与「提额走人工」；
  适当性不匹配说明「验码也覆盖不了」；不猜名字（歧义就澄清）。
- **续费提醒**：查询订阅时附带「未来 7 天将自动扣费 ¥X（N 笔）」，只算窗口内，
  让用户回答的是「这张卡下周会不会被扣穿」，而不是「我有几个会员」。
- **语音输入不是旁路**：只把话转成文字填进输入框，由人核对后再发，走同一条管线。

## 6. 部署与运行

```bash
python -m pip install -r requirements.txt
python run.py            # http://127.0.0.1:8000
python selfcheck.py      # CI 与本地共用同一条验收命令
```

- 演示库 `data/bank.db` 由 `app/bank/seed.py` 生成（`seed(reset=True)`）。
- 令牌密钥写在 `data/.auth_secret`（若未配 `JH_AUTH_SECRET`），**已被 .gitignore 排除**。
- 真模型：复制 `.env.example` → `.env`，设 `JH_LLM_MODE=openai` 与 `JH_LLM_BASE_URL/KEY/MODEL`。
  demo / pytest / eval 三套验收**强制走 mock**，保证结论可复现。
- CI：`.github/workflows/ci.yml` 在 ubuntu-latest 上跑同一条 `python selfcheck.py`。
