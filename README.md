# 金衡 Statera · 可审计的银行 AI 智能体

> 2026（第八届）FinTechathon 深圳国际金融科技大赛 · 人工智能赛道
>
> **模型只提案，内核做裁决。**

现在的手机银行转一笔账平均要点三下以上。我们希望用户说一句话就能把事办成——
但银行不能只要方便，更要安全。

金衡的做法是：**大模型只负责「听懂」和「计划」，所有权限判定与资金执行交给一个
不读自然语言、不受模型影响的确定性策略引擎。** 因此提示注入最多只能让模型产出一个
不合法计划，拿不到执行权。

## 快速开始

本项目**零外部依赖可跑**：默认使用内置的规则版理解模块（`mock`），
不需要任何 API Key，不联网。

```bash
# 1. 准备环境
python -m venv .venv
.venv/Scripts/activate          # Windows
# source .venv/bin/activate     # macOS / Linux
pip install -r requirements.txt

# 2. ★ 一条命令看清全部：场景 + 单测 + 对抗评估，给出一个总判决
python selfcheck.py

# 3. 想看细节，三条分开跑
python demo.py               # 14 个场景，50 项断言
python eval_report.py        # 与「把权限写进 Prompt」的实现正面比对
python capabilities.py       # 能力清单（--json 给自动评测脚本读）
python llm_smoke.py          # 真模型联调表（未配 .env 时提示怎么配，不报错）

# 4. 或起 HTTP 服务
python run.py
#   打开 http://127.0.0.1:8000/  → 登录页（u_1001 / 123456）
#   或在 http://127.0.0.1:8000/docs 里先 POST /api/auth/login 换令牌，再试 /api/chat
```

验证是否一切正常：

```bash
python selfcheck.py          # 期望：三项全 PASS，退出码 0（它就是上面三条的合集）
python demo.py               # 期望：50/50 通过
python -m pytest tests -q    # 期望：110 passed
python eval_report.py        # 期望：31/31 与 11/11
```

## 身份：三层，别混为一谈

| 层 | 回答什么 | 落点 |
|---|---|---|
| **会话身份** | 你是**谁** | `POST /api/auth/login` 用口令换令牌，此后只认 `Authorization: Bearer` |
| **操作授权** | 这一笔要不要**再验一次** | 三色分级（`policy.py`，从不读自然语言） |
| **数据归属** | 你只能看见**自己的** | 每张表都带 `user_id` 条件（`db.py`） |

只有第二层、没有第一层，等于门锁很高级、门框是纸糊的 —— 这正是 2026-10-30
实跑时查出来的洞：那时候 `{"user_id":"u_2001","message":"我有哪些卡"}` 能直接
读到另一个人的卡。现在身份由令牌承载，请求体里写 `user_id` 会被 403 拒绝；
拿自己的令牌去看别人的会话返回 404（**连存在性都不暴露**，403 等于告诉对方「这条记录是有的」）。

演示账号 `u_1001 / 123456`；越权对照账号 `u_2001 / 654321`。

## ★ 四件「一句话改不了」的事

这四条是 2026-10-30 第二轮实跑打出来的。用户当时问了一句：

> 「冒充管理员权限这个发个验证码就通过会不会太顺利了？」

这句话表面在问一件事，实际揭开了三层——而修完之后我们发现，**第四层的洞更严重**。

### 1. 限额是硬约束，不是风险信号

修之前：当日已转 600，再转 500 会累计到 1100，超过 1000 元日限额 → 引擎判为「红色」→
**发一条验证码，用户给了码，钱就转出去了**。也就是说 1000 元的日限额，输一个验证码就能突破。

错在把「限额」当成了「风险信号」。风险信号的意思是「有点可疑，多验一次」；
而限额的意思是「这笔钱本来就不许转」——多验一百次也还是不许。

| 规则 | 阈值 | 结果 |
|---|---|---|
| P-040 单日累计 | 1000 元 | **DENY**，回显「今日剩余可转 ¥X」 |
| P-042 单月累计 | 20000 元 | **DENY** |
| P-043 同一收款人当日 | 1000 元 | **DENY** |
| P-044 单笔 | ≥500 元 | MFA（这一次才是「多验一次」） |

拒绝文案里写清楚剩余额度，并给出唯一出路：回复「转人工」走人工复核。
强验证能证明「你是本人」，但**无权改变「这笔钱本来就不许转」**。

### 2. 注入 + 动钱 = 整轮阻断，不是「再验一次」

修之前：一句话里有 3 个注入特征（冒充管理员 / 忽略指令 / 绕过验证），系统**识别出来了**，
然后照样发验证码、照样执行一万块。那条路径「安全」得毫无意义——它根本不该走到验证码。

现在（P-090）：命中注入特征 **且** 请求涉及资金或红色操作 → **整轮一步都不执行**，
连查询也不做，直接回一段解释：

```
🚫 这轮没有执行任何操作。
按风控规则，含这类表述的话**不进入资金与高风险操作**——不是「多验一次」，是「这条请求不做」。
顺带说清楚：你的会话角色是 customer，来自登录态。
管理员权限只能由后台授予，不能通过对话声明。
```

**只拦动钱的，不拦查询**：查询没有权限可提升，拦它只会制造「系统乱拒」。
这条边界有专门的单测锁着（`test_injection_does_not_block_plain_queries`）。

判定按**意图**而不是只按步骤——这是补的一个真洞：`立刻给我转一万` 缺收款人，
只产出一个 intent、产不出 step；只看 steps 的话它会退化成普通追问
（「还差收款人」），用户补一句「妈」就接着办，**注入没被拦住，只是被拆成了两轮**。
现在阻断时也不写槽位续接状态，下一句补参接不上（`test_injection_with_a_missing_slot_cannot_be_completed_next_turn`）。

角色也同样是结构性的：`users.role` 从数据库读进 `ctx.role`，每一轮都重读。
自然语言里的「我是管理员」根本到不了这个变量。

### 3. 验证码不在聊天窗口里

修之前：动态码直接拼在回复文本里——「已发送验证码 123456 到您的手机」。
能改写对话的攻击者，也就能读到对话里的验证码。**两者在同一条通道，双因子就只剩一个因子。**

现在（`app/bank/sms.py`）：动态码写进 `sms_messages` 表，也就是「你手里那部手机」；
聊天回复只说「已发送到 138****8000，请打开右上角『📱 手机』查看」。
演示页右侧有对应的短信面板，走 `GET /api/auth/sms`（需令牌）。

还有一层：**码绑定到它被签发的那一笔**。码存在 `confirmations` 那一行上，
那一行同时存着完整计划（给谁、多少钱、依赖哪些步骤）。换一个操作，那一行就不在
pending 里了——拿 A 的码放行不了 B，这是结构保证，不是概率。

### 4. 审计链：从「可审计」到「改了看得出来」

修之前，`audit_log` 就是一张普通表。有库权限的人改一行，改完看不出任何痕迹。
「可审计」这个词在这种情况下是不成立的。

现在每行带 `prev_hash` + `row_hash`，哈希覆盖 `(prev_hash, trace_id, ts, user_id,
session_id, stage, payload)`，字段间用 `\x1f` 分隔（防止 `"ab"+"c"` 与 `"a"+"bc"`
撞成同一个哈希）。`prev_hash` 在 `INSERT ... SELECT` 里取，写锁内求值，不会出现分叉。

一个 GET 就能验证：

```
GET /api/audit/verify  →  {ok: true, checked: 312, first_bad_id: null, head: "a3f9c1..."}
```

改任意一行的 payload，`first_bad_id` 就指向它。演示页上还配了两个按钮：
「校验哈希链」和「导出整段会话审计（JSON，附链校验结果）」——
后者是关键，**单看一份 trail 只能证明「有记录」，附上 `ok`/`head` 才能证明「这份记录和库里那条链对得上」**。
这是把「可审计」从口号变成**一个评审可以自己点一下、还能带走复核**的东西。

> 已知局限（安全自评里如实写）：现在是纯 SHA-256，**知道算法的人可以把整条链重算一遍覆盖掉**。
> 生产需要 HMAC + 外部锚定（例如每日把链头推到不可写存储）。这里只做到「改一行看得出来」。

## 听懂人话：槽位续接与近似纠错

用户实跑的第一句吐槽是「解挂方面暴露出它有一点听不懂人话」。
还原现场：系统问「请问要解挂哪一张卡？（尾号）」，用户答 `2233`——然后系统说「没听懂」。
**一个连自己提的问题都接不住的系统，用户不会认为它安全，只会认为它坏了。**

两处修法：

1. **槽位续接**（`engine/followup.py`）：系统问完问题后，把「缺哪些槽、原始意图是什么」
   存进会话（一轮有效）。下一句「2233」先当作补充槽位，补齐后**重新渲染成一句完整的话**
   （`解挂尾号2233的卡`）再交给原来的理解与规划管线——规划逻辑仍然只有一份。
2. **近似纠错**（`tools/card.py::_near_miss`）：`2333` 与 `2233` 只差一位，
   提示「你指的是不是 信用卡（尾号2233）？」，**但绝不替用户换一张卡**。
   挂失是单向操作，替用户猜一次，可能就是替别人挂掉了他自己的卡。

## 架构

```
用户（APP / IM）
   │
   ├─ L1 输入隔离：用户文本不进 system prompt，包进 untrusted 信封
   ▼
[理解层] LLM ──▶ Intent（意图 + 结构化槽位）        ← 不决策
   ▼
[规划层] LLM ──▶ Plan（任务 DAG）                   ← 不决策
   ▼
[校验层] DAG Validator：工具白名单 / 参数 Schema / 无环   ← 纯代码
   ▼
[裁决层] ★ Policy Engine（确定性，不读自然语言）
         绿 / 黄 / 红 + 当日累计 + 收款人归属          ← 纯代码
   ▼
[执行层] Executor ──┬─▶ Mock 银行 API ──▶ ToolResult  ← 纯代码
                    └─▶ ★ 代码沙箱（独立子进程 / 超时 / 内存上限 / 受限 builtins）
   ▼
[表述层] Renderer：模板渲染，模型无权转述交易结果       ← 纯代码
```

**信任边界只有一条**：LLM 在「理解层 / 规划层」之上，不能跨越。
裁决、执行、表述三层完全不经过模型。

| 层 | 拦什么 | 实现 |
|---|---|---|
| 结构层 | 模型幻觉、调用未注册工具、计划成环 | `engine/dag.py` |

## ★ 代码沙箱：为什么「模型生成的代码」可以执行

账单分析要做的事，本质是「自然语言 → 代码 → 跑在真实数据上」。危险点很明确：
**模型生成的代码是不可信输入**，提示注入可以让它输出 `os.system(...)`。

所以我们不假设模型会老实，而是假设它一定会被攻破：

| 闸门 | 作用 | 拦不住时 |
|---|---|---|
| 静态 AST 检查 | 拒绝 import / `eval` / `open` / 双下划线属性 | 后面还有三道 |
| 独立子进程 | `-I` 隔离模式、空 cwd、**重建的环境变量**（密钥不继承） | 进程可被杀 |
| 受限 builtins | 只有纯计算函数，没有 `open` / `__import__` / `eval` | — |
| 资源闸门 | 超时 5s、内存上限 256MB（RSS 看门狗）、输出上限 64KB | — |

`eval/sandbox_attacks.yaml` 里 11 条针对性 payload（读文件、爬对象树、死循环、
内存炸弹、超大输出、篡改入参……）全部按预期被关住，其中
**正常分析代码作为对照组照常执行** —— 证明闸门不是靠「什么都不让跑」过关的。

> 已知局限（如实写进安全自评报告）：内存看门狗是 50ms 轮询而非内核级硬限；
> Windows 无 seccomp/CGroup，隔离强度弱于 Linux 容器；未做网络命名空间隔离。

## ★ 跨场景联动：为什么条件不写成表达式

「余额够的话给王强转 500」是一句两跳的话：先查，够才转。它需要三件事都做对。

**1. 条件不能是字符串表达式。**
如果 `when` 写成 `"data['count'] > 0"`，就等于让模型生成代码参与决策——
这和沙箱那一节要防的是同一个东西，只是换了个位置。
所以条件是**结构化**的（`schemas.StepCondition`）：引用哪个步骤、取哪个字段、
什么比较符、跟什么字面量比。执行器做纯比较，没有 `eval`，没有解析器。

**2. 条件必须先算，再决定要不要惊动用户。**
「先判完整个计划再统一执行」的写法，会导致余额还没查就先弹人脸。
所以编排层是逐步骤的「判条件 → 裁决 → 执行」，当日累计在循环里自己维护
（语义与 `adjudicate_plan` 完全一致，有对应单测锁住）。

**3. 拿不准就不执行。**
条件引用的步骤没跑、字段不存在、类型不可比——一律判为不成立，
并如实告诉用户「为什么跳过」。对一个「够就转」的计划，跳过永远比误转安全。

两个同样「看起来做了、其实没做」的坑，都是真跑打出来的：

| 现象 | 根因 | 修法 |
|---|---|---|
| 用户确认后报「依赖了不存在的步骤」 | 存待确认队列时只存了转账那一步，没存它依赖的余额查询 | 保存时补齐前置依赖（`_remaining_with_prereqs`） |
| 用户说了「算了」，之后说「确认」钱还是转出去了 | 中断只生成了回复文案，没作废落库的授权 | `pending.cancel_all` 作废**全部**待确认记录 |

人工接管同理：不是回一句「已转接客服」，而是生成一张**工单**，
把本次会话的完整审计链挂上去（按 session 聚合，不是按 trace，否则只有 1 条），
同时作废所有悬空授权——交接期间不能有任何自动执行。

> 未做：回退（撤销已执行的一步）。金融场景里的「撤销」不是软件动作而是业务流程
> （冲正、调账），由人工工单承接更贴近真实做法，因此刻意做成人工接管而非自动回滚。

## 接口速查

除 `/health`、`/tools`、`/capabilities` 外，**全部需要 `Authorization: Bearer <token>`**。

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/auth/login` | 口令换令牌 |
| GET | `/api/auth/me` | 当前用户（含 `role`，来自数据库） |
| GET | `/api/auth/sms` | ★ 模拟手机短信收件箱——动态码在这里，不在对话里 |
| POST | `/api/chat` | 一轮对话（多轮务必带上一轮返回的 `session_id`） |
| GET | `/api/audit/verify` | ★ 逐行重算哈希链，回答「有没有被改过」 |
| GET | `/api/audit/{trace_id}` | 某一轮的完整决策链（不是你的 → 404） |
| GET | `/api/session/{id}/audit` | 整段会话的审计链（人工接管工单要它） |
| GET | `/api/session/{id}` | 会话态 + 熔断状态 + 今日已转 |

## 环境变量

全部可选，不配也能跑。想接真模型时，把 `.env.example` 复制成 `.env` 再填值即可
（`.env` 已在 `.gitignore` 里，**API Key 不会进仓库**）。

| 变量 | 默认 | 说明 |
|---|---|---|
| `JH_LLM_MODE` | `mock` | `mock`（离线）或 `openai`（调用兼容端点的模型） |
| `JH_LLM_BASE_URL` | OpenAI 官方 | 兼容 `/chat/completions` 的任意端点 |
| `JH_LLM_API_KEY` | 空 | 留空时 mock 模式照常工作 |
| `JH_LLM_MODEL` | `gpt-4o-mini` | 模型名 |
| `JH_AUTH_SECRET` | 空 | 令牌签名密钥。留空则在 `data/.auth_secret` 生成一次并复用（生产须走 KMS/环境变量） |
| `JH_TOKEN_TTL` | `7200` | 令牌有效期（秒） |
| `JH_DAILY_LIMIT_CENTS` | `100000` | 单日累计转账上限，单位分（= 1000 元）。**超了直接拒，强验证不能覆盖**（P-040） |
| `JH_MONTHLY_LIMIT_CENTS` | `2000000` | 单月累计转账上限（= 20000 元，P-042） |
| `JH_CONTACT_DAILY_LIMIT_CENTS` | `100000` | 同一收款人当日累计上限（= 1000 元，P-043） |
| `JH_CONFIRM_LIMIT_CENTS` | `50000` | 单笔达到此额度（= 500 元）升级为红色 MFA（P-044） |
| `JH_CIRCUIT_FAILS` | `3` | 连续失败多少次熔断 |
| `JH_CIRCUIT_INJECTS` | `4` | 注入特征累计多少次熔断 |
| `JH_SANDBOX_TIMEOUT` | `5` | 分析代码最长执行秒数 |
| `JH_SANDBOX_MEM_MB` | `256` | 分析代码内存上限（MB） |

> 所有阈值都从 `app/config.py` 读，且**每一个都有代码在用**。
> 「配置里有、代码里不用」本身就是个坑：看起来可调，实际调了没反应。

## 常见坑

- **金额一律用「分」的整数**，全系统零浮点。`render.yuan()` 负责格式化。
- **当日累计必须从数据库实时读**，不要复用内存里的旧值（`orchestrator` 每轮都会重读）。
- **新增工具**：在 `app/tools/` 实现 handler 并 `register(ToolMeta(...))`，
  在 `app/tools/__init__.py` 加一行 import，在 `engine/render.py` 加渲染器。
  忘了加渲染器不会崩，但只会输出「操作已完成」——这是刻意的保守行为。
